# 48 — Experience surfaces and interaction contracts

> Status: DEC-055 target design; implementation and usability evidence pending. This document owns the final user-facing HLD/LLD. `AGENTCOWORK-UI.md` describes the earlier v1 baseline where it conflicts. Requirements live in `08`, architecture ownership in `03`, and tests in `49`. Capability availability must be shown from a live probe, never inferred from a provider name.

## 1. Experience rule

The first screen is an ordinary conversation: ask, attach, send. A question gets an answer. A request for work becomes a visible task. A durable or parallel goal becomes a Mission. The user can expand detail at any time; the product also exposes detail when work, risk or uncertainty makes it useful. No user must understand Work, ACP, DAGs, MCP or tickets to complete an ordinary task. These terms are available in an Advanced view and diagnostics. One conversation can contain answers, tasks and Missions without forcing a separate product mode.

The UI has three resizable regions: left navigation, conversation, right Workbench. On a narrow window, navigation becomes a drawer and Workbench becomes a full-width tab or sheet; neither is silently discarded. A persistent status strip shows running work, a needs-you count and the location of execution (this computer, remote host, or external agent). Every visible state must distinguish planned, running, waiting, reported complete and independently verified. A worker's self-report never earns a verified badge.

## 2. Primary navigation and first-run

| Area | Default content | Expansion |
|---|---|---|
| Home | New conversation, recent work, resume card and three outcome examples | Templates and pinned projects |
| Conversations | Searchable recent threads, running/waiting badges, grouped by project | Filters, archive, export, lineage |
| Tasks | Current and scheduled work with simple status, result and needs-you | Mission graph, agents, costs, timeline and evidence |
| Files | Workspace folders and recent files | Worktrees, versions, indexing and storage |
| Automations | Saved routines, schedules and triggers | Workflow editor, runs, waits and failures |
| Library | Generated, uploaded, imported and linked artifacts; saved skills/templates | Provenance, dependencies, indexing, versions |
| System | A plain-language view of this computer’s current health and recent trends | Processes, hardware/GPU, storage, network, history and query under explicit scopes |

The left sidebar contains the primary destinations above, current project/workspace switcher, New button, search, running task badges and recent conversations. In Tasks, keep scheduled, active, waiting and recent work distinguishable; persistent agent identities can stay pinned above ad-hoc work, while ordinary task order remains stable as status updates arrive. Each row gives one clear status, a short outcome or needs-you message, and an unread marker only for a new consequential result since the user last opened it. The compact rail retains agent identity and status with accessible labels; hover previews are an enhancement, never the only way to learn status or open actions. On touch layouts, use a named action sheet instead of hover menus. Loading, empty, failure and stale states are distinct, and rapid task/file switching must not allow an older response to replace the current selection. Account/profile at bottom opens Settings. It is collapsible and keyboard navigable. Agents, Connections, extensions and diagnostics are reached through Settings, contextual controls and command search; they do not crowd first-run navigation. A user may pin any advanced destination to the left sidebar.

First-run sequence: choose a workspace or begin with chat; discover local agents in the background; show only verified ready agents; offer a guided connection when an action needs one; demonstrate one reversible local task; show permission and data-location explanation at the point of use. Slow CLI probing cannot block the first interactive prompt. Empty states explain a concrete outcome, not platform jargon.

## 3. Composer contract

The composer is one box with a multiline editor, attachment chips and a compact footer. Default footer, in reading order: `+`, agent selector (`Auto` unless pinned), model selector only when the selected agent supports choosing models, autonomy/access chip, voice control when installed and authorized, Send/Stop. Send-now is the default. The send menu exposes background execution and Schedule when supported; a natural-language time/recurrence/event request is also recognized into a reviewable schedule preview before it is saved. This keeps scheduling reachable from chat without making a casual message look like a workflow editor. Running work also exposes Queue and Steer; sending while active asks whether the message steers now or queues next, with an undo window. Enter sends, Shift+Enter adds a line; accessible shortcuts are configurable. The draft, attachments and selections survive navigation, questions, agent changes and crashes.

| Control | Behavior and failure state |
|---|---|
| `+` | Add local files/folders, image, screenshot, clipboard, URL, Library item, current Workbench selection, or connect an app. Recent sources first; show size, sensitivity and upload/index scope before attaching. Folder attachment means a scoped reference, not dumping all bytes into a prompt. |
| Agent | Lists ready/recent agents plus `Auto`; each row shows local/remote, ready/needs sign-in/unavailable and verified abilities. A gear opens that agent's Settings detail. Selecting another agent in an idle conversation switches the next turn in the **same visible conversation**; it must not create a new thread or mutate an active Work. If work is currently running, show “Current task keeps running with [agent]; [new agent] will handle your next message” plus Stop-and-switch where supported. The prior agent's own attached session is retained for quick return when supported. Picker never pretends to move a native transcript between agents. |
| Model | Shows advertised models for this agent and account, searchable with cost/availability when known. If the agent controls its own model, show `Managed by agent` and link to native settings. Never pretend a model picker can control an external CLI that does not expose one. |
| Compare approaches | Secondary action in the Agent picker; select compatible workers or ask for a budget-bounded diverse set. Reuses the exact prompt, references and contract for each candidate. Show count, cost/concurrency, write isolation and each worker's tools/access profile before launch; disclose when different agents make it a worker-system comparison rather than a model-only comparison. Candidates without safe write isolation or bounded native permissions are read-only, excluded, or require explicit review before start. Ordinary chat has no extra always-visible control. |
| Autonomy/access | Plain choices: `Ask before changes`, `Allow workspace work`, `Custom`. A detail sheet shows effective file, network, connector, browser and desktop grants; native-agent policy is shown separately. Temporary grants have scope and expiry. A label must not promise Core control over native calls. |
| `@` | Insert a structured reference to file/folder, Library artifact, project, open Workbench tab or selection, person/connected resource, or a ready agent for a directed task. Search is scoped and privacy filtered; insertion stores an identity/version/selection range, not only a display name. Missing or stale references are flagged before send. |
| `/` | Search command palette with namespaces: app actions `/cowork:*` (for example `/cowork:plan`, `/cowork:agents`, `/cowork:attach`, `/cowork:skill`, `/cowork:resume`) and supported native agent commands under that agent's own namespace. Never hijack an agent's native slash command; unknown commands remain ordinary text until explicitly chosen. Suggestions disclose effects and shortcuts. |

Attachment intake is capability-aware and has an explicit destination: **attach for this message** or **add to Library/workspace**. The first is a version-pinned, conversation-scoped reference and does not silently persist/index the source; the second creates a visible ingest job with progress, parser/coverage, retry and removal state. The composer filters or labels file operations against the selected agent's probed input support, while still allowing a user to keep the file selected and choose a compatible worker. Multiple files enter one ordered queue from `+`, paste or drop; a partial upload/extraction failure identifies only the affected items and preserves the prompt and successful attachments. A model's ability to receive an image or filename does not imply it can parse PDF/DOCX/XLSX bytes; show the actual processing route and fallback before send.

Agent and model choices are per logical conversation by default; an explicit task override applies only to that task. Picker changes during a Mission create a replacement or future-assignment proposal and preserve current work until the user confirms the action. Each sent turn records the selected binding, provider-qualified model (or `agent-managed`), supported handoff references and effective extension grants. Switching constructs a bounded handoff from the visible conversation and selected versioned refs; the user can inspect/edit the handoff when continuity is ambiguous. Private native transcript and memory are never copied. Keep prior agent-session handles attached for fast return if supported; probe/reauth status is cached with a freshness stamp and refreshed without blocking the message editor. Disabled controls explain why (offline, missing capability, auth, policy). The footer stays compact; advanced effort, context, budget and routing controls live in an expandable detail popover. A reasoning-effort control appears only when the selected agent/model advertises supported levels; it offers only those levels, clamps or resets explicitly on agent/model change, keeps `Auto` distinct from measured effort and explains when the native agent owns that setting. Never expose a decorative toggle that has no execution effect.

## 4. Conversation and results

Messages render CommonMark/GFM, syntax-highlighted copyable code, keyboard-scrollable tables, inline/display equations, citations and responsive media cards. Streaming must remain responsive for long answers: preserve exact source text, update at most once per animation frame, reuse completed blocks, defer expensive body work, and do not repeatedly syntax-highlight an unfinished code fence. When the user scrolls away from the live edge, new output must not take over scroll position; a clear return-to-latest affordance appears. Long histories use measured windowing or equivalent bounded rendering without breaking find, selection, accessibility or restored scroll position. Only committed code blocks are syntax-highlighted. In-flight text remains readable plain monospace.

### 4.1 Markdown, math, media and diagram contract

- Apply the product theme to headings, paragraphs, lists, blockquotes, rules, tables and media. GFM tables stay inside a keyboard-focusable labelled region and never widen the conversation column. Code blocks expose language when known, copy, wrap/scroll and a polite copy result; clipboard or highlight failures have visible fallbacks.
- Raw HTML in model-authored Markdown is disabled. Links route through the approved browser-opening path; missing local files are inert with a reason. Remote images do not load silently: show a placeholder and require the applicable host/content policy before network retrieval. Every image has bounded dimensions, reserved aspect ratio when known, alt text or an explicit missing-alt marker, optional caption and an accessible zoom/lightbox. Broken or oversized images preserve a safe open/download action.
- Inline and display math use a constrained renderer with untrusted extensions disabled and bounded expansion/size. Keep the source available to copy and expose it as an accessible fallback; a malformed expression shows a local error label and the original expression instead of breaking the message. Screen readers receive the semantic expression once, not both visual glyphs and duplicate source.
- A closed `mermaid` fence may convert automatically without a model call. Never render a partial fence. Gate untrusted source, cap input (50,000 characters), graph size (500 edges) and render time, force strict security options and block source overrides of the security/theme configuration. Render the result as a non-interactive image in an isolated path, not privileged inline SVG/HTML. Reserve its aspect ratio and keep the previous successful render visible during a theme change. Rejection or renderer failure leaves copyable source, a status explanation and an explicit retry. Static Generative UI previews remain opt-in; transcript diagrams are part of the answer and can render locally without a model call.
- Interactive HTML/SVG artifacts are not Markdown. They use an isolated preview origin/context with an explicit capability bridge; no script, link, image, download or network action receives app privileges by inheritance. If preview fails or is blocked, keep source and a safe download/open action.

These rules apply to streamed and committed messages. A render, citation lookup, Mermaid conversion, reference extraction or tab open must not invoke a model. Reserve live-region space to prevent content/layout shift; use polite announcements for meaningful status transitions, never token-by-token speech. `REQ-UI-001…009` and `REQ-UI-014` define the testable details.

### 4.2 Work activity and planning visibility

Tool activity has five user-facing states: `proposed`, `running`, `succeeded`, `failed` and `cancelled`. Streaming is `running` with progress events, not a sixth state. Group calls under one turn-level activity rail; a settled turn may collapse to a concise summary, but groups with an error remain open until the user reviews or closes them. A policy denial is neutral, lock-marked and explained; red denotes an actual failure. Group identity is stable across replay/reordering. Tool-specific result renderers (diff, terminal, file, search, form, checklist) are registered by result type and fall back to a safe generic row. Large payloads stay out of the transcript until explicitly expanded; failed and blocked outcomes never disappear into a collapsed group.

For an agent-provided plan, show a compact plan strip above the composer only while it belongs to the active turn. It is keyboard-operable, announces completed/total only when those values are known, and expands within a bounded height. A revised plan reports a real delta only when the previous version is known; otherwise it says that the plan changed without fabricating a comparison. Each step reuses the canonical status vocabulary and links to its verification evidence. No plan means no strip and no reserved gap. A plan strip is a view of the active agent's plan, not Mission truth; durable Mission milestones and PlanNodes remain in Tasks/Mission Control.

Reasoning/progress details are closed by default and summarize activity. Raw chain-of-thought is never persisted or displayed. A user override of the disclosure state wins for that turn; the product can hide the summary entirely. Meaningful transitions (waiting for permission, tool running, verification failed) are announced; timers and streaming tokens are not repeatedly announced. Diffs use one renderer in both approval cards and Workbench tabs. Review controls must match actual rollback/restore support; if only whole-file accept/reject exists, the UI says so instead of displaying decorative per-hunk undo.

### 4.3 Artifact cards in the conversation

Every answer with generated media or files presents an artifact card beside its explanation, with Open in Workbench, Save to Library, version, source and verification state. A user can edit a draft response or artifact, compare versions, restore a version, copy/export and ask the chat to change the exact selection. Citations are claim-linked where feasible. Failed preview is an explicit fallback/download action, not a blank pane. Voice, images and attachments must preserve transcript/draft and have keyboard equivalents.

## 5. Right Workbench

The right pane is a dockable, resizable multi-tab Workbench. Opening a chat citation, file, browser state, artifact, diff or agent automatically creates/focuses a tab while preserving other tabs. One stable resource identity/version maps to one tab; opening the same item focuses it, while distinct documents of the same format can remain open together. Persist lightweight references and tab state, not duplicate file bodies. Tabs have type icon, title, dirty/unsaved indicator, version and close confirmation. Split view supports two items side by side. The chat can refer to the active tab or selected text/cells/slide/DOM element via structured references; the scope is visible above the composer. Selection changes must not silently redirect an already-running agent.

Panel behavior should stay fast and compact as tabs grow: mount heavy viewers on demand, retain the selected tab per Work, allow pinning, and show independent task state for Files, Planner, Browser and Terminal. This is a source-backed interaction pattern in OpenHands Agent Canvas [`conversation-main.tsx`](https://github.com/OpenHands/OpenHands/blob/f174ba8465233e46e66ab2c5667b358f1d6676d6/src/components/features/conversation/conversation-main/conversation-main.tsx) and [`conversation-tabs.tsx`](https://github.com/OpenHands/OpenHands/blob/f174ba8465233e46e66ab2c5667b358f1d6676d6/src/components/features/conversation/conversation-tabs/conversation-tabs.tsx). AgentCowork extends that pattern with the document handler registry, artifact versions and safe native-app handoff below; the external reference is recorded with limits in `ARCH/45-REFERENCE-RESEARCH.md` “OpenHands Agent Canvas.”

| Tab | Minimum behavior | Editing and verification boundary |
|---|---|---|
| Browser | Managed Chromium tab with URL, navigation, history, download shelf, screenshots, DOM/accessibility selection, agent action markers and Take over/Return control | Use a managed profile for reliable automation. Attaching a user's Chrome requires supported remote-debug/extension bridge and explicit consent; arbitrary Chrome embedding in the Tauri webview is not assumed. Auth handoff and session ownership are visible. |
| Files/tree | Current workspace or isolated worktree tree, search, breadcrumbs, file status and diff badges; click opens a suitable tab | Save uses file identity, conflict check and atomic write; native-app open fallback for unsupported formats. External native-agent edits can be observed but not retroactively ticketed. |
| Any other file type | Every selected file gets a Workbench tab. A shared handler registry probes content/MIME/extension and offers safe metadata, preview, extraction or editing only where a registered provider advertises it | With no matching handler, show a generic metadata tab and a user-chosen **Open with…** action; track the native-app handoff and file changes, surface conflicts and rebind chat to the new file version. File selection never runs content; executable/script/shortcut/installer files use a distinct Trust-gated action, and untrusted active-content documents disclose native-app behavior before opening. Never claim content was read or changed when only a path was opened. |
| Text/code | Large-file virtualization, syntax and diff, line references, edit/save/undo | Concurrent changes prompt compare/merge; code changes can be reviewed as patch/worktree. |
| PDF | Fast pagination, thumbnails, bookmarks, search, text selection, annotation and citation/page anchors | Editing is annotation or explicit transformation into a new artifact unless a provider supports structural PDF edit; scanned PDFs require OCR with confidence shown. |
| DOCX | Paged reader with headings, comments/changes and print preview | Editing uses a capable provider or native app; round-trip fidelity check shows unsupported features before save. |
| XLSX/Sheets | Grid, sheets, formulas, charts, filters, ranges and recalculation status | Typed cell/range edits, formula recalc and validation; macros/external links are not executed merely by preview. Unsupported pivots/visuals get an honest warning/native fallback. |
| PPTX | Slide thumbnails, speaker notes, master-aware preview and presentation mode | Edit via provider with render comparison; unsupported animations/media are flagged. |
| Image/media | Zoom/pan and metadata; time-based media player and transcript if available | Edit operations make a new version; source and generated status stay visible. |
| Mission/agents | Goal, current step, per-worker status, child tree, blocker, timeline, cost and evidence | Steer, pause, replace, inspect or take over at supported boundaries. Native subagents without a reported lifecycle are shown only as reported/observed, not invented. |
| Compare | Candidate cards on one comparison PlanNode: agent/harness/model, actual tools/access policy, status, output/artifact or diff, criterion-level evidence, cost/time, and verified isolation state | User may open a candidate, select it, or request separate integration from a clean baseline. Failed candidates remain visible. Core-mediated effects still need selection and normal Trust authorization. Native effects remain under the agent's policy and are not shown as Core-blocked; make that boundary clear before launch. |
| Workflow/artifact | Workflow graph or artifact viewer with versions, dependencies and input sources | Draft changes and run previews; publish requires validation and applicable policy. |
| System | Overview starts with CPU, memory, storage, network and available GPU summaries; freshness and “why unavailable” are written for a nontechnical user | Advanced tabs expose Processes, Hardware & GPU, Storage, Network, History and Query; an in-app consent dialog appears before the first read, including when an agent requests a category. Process/network/history scopes have separate controls. Opening this tab does not attach readings to chat. |

“Any file” means the universal Workbench can open a tab and route to the strongest safe available handler, not that every proprietary format has a built-in renderer/editor. Probe content and per-operation support, offer a generic file tab and native-app handoff when needed, and never silently corrupt or flatten a file. Chat always retains the selected file identity/version; semantic reading or edits require a compatible provider and scoped access. The Workbench's browser shares a controlled session with the agent only when the binding supports it; otherwise it displays a live/recorded observation with the limitation stated. The user can always stop/take over an active managed browser/desktop run. When takeover ends, the worker must resnapshot state before acting.

## 6. Library, knowledge and retrieval

Library filters: All, Generated, Uploaded, Imported, Linked, Saved templates, Skills and Workflows, with project/source/type/date/verification/staleness facets. Items show title, type, size, author/source, creation/update time, active version, origin Mission/Work, permissions, indexed status, input dependencies and downstream use. Search covers names and extracted content only for permitted/indexed items. Preview and metadata work while extraction is pending. OCR/transcription/extraction record version, parser, coverage and errors; retrieval cites the exact artifact version and location (page, cell, slide, line or time span). Re-index on content/version change; revocation or deletion removes retrieval exposure and caches according to retention policy. Uploaded bytes are never treated as trusted instructions. Saving an artifact to Library is explicit; derived versions remain linked to original inputs.

## 7. Settings, agents and extensions

Settings uses a searchable grouped index, not a wall of equal-weight tabs: Personal (General, Appearance, Accessibility, Notifications); Work (Agents & models, Connected apps, Browser & computer, Tasks & automations); Data and access (Files & Library, Privacy & permissions, Secrets); Advanced (MCP/skills/plugins, diagnostics, storage, import/export). Each page has a plain-language summary, effective state, source and reset/revoke where meaningful.

Settings fields are generated from a typed registry with a unique key, parser, owner and scope (`device`, `user`, `workspace`, `agent`, `conversation` or `mission`). Effective values show their source and revision; invalid or unknown keys are rejected. Device-only cosmetic preferences may remain local. Authorization, connector access and extension grants remain in Core with monotonic revision and cannot be changed by a stale renderer write. Named profiles contain non-secret overrides, preview effective changes before apply, and never copy credentials. A dirty form offers Save, Discard and Cancel on navigation. Settings search indexes labels and synonyms and opens/highlights the matched field; the shortcut catalogue and dispatcher share one registry with collision checks. Window resize, reduced motion and keyboard/screen-reader behavior apply to every group (DEC-056).

Agents page shows Ready, Needs setup, Discovered and Disabled lists. Each detail displays executable/source/version, health/probe time, verified capabilities, supported transports, actual model/provider choices, native auth state, Core-managed account option if compatible, allowed workspaces, default roles, concurrent sessions, quotas if known, native extension inventory (read-only when discovery supports it), and shared capability grants. A **Subagents** section provides the per-binding `Available as a subagent` enable switch. Enabling opens a configuration panel showing only models that this binding reports and Core verifies it can select; the user pins one exact provider-qualified model, or explicitly selects `Agent-managed` if permitted. The panel also sets allowed task roles, extension ceilings, isolation, concurrency/depth and budget ceilings. Include the lead agent itself as an eligible child profile when it can create a separate session; its child receives a fresh context and the pinned child model, not the lead's transcript. If per-session model selection is unsupported, the model pin is disabled with the reason and a fixed/default or explicit agent-managed policy must be chosen. Native subagent settings stay inside the agent and are not rewritten.

Sign-in invokes the agent's supported native flow; API key entry is only offered for a verified supported provider and is held by the owning agent or Core vault according to custody. Never advertise every vendor for every agent. Install is isolated and reversible; discovery is read-only and never rewrites the user's agent config. Reprobe, disable, update and remove show impact on running and saved Missions. Horizon Code is a future external binding, not a shipped agent.

MCP servers, skills and plugins have distinct states: catalogued, inspected, installed, connected (when needed), enabled for a binding, and active for a specific Work/session/workspace/Mission. Effective access is the intersection of owner scope, package permissions, agent compatibility, task grant and policy. A discovered agent's native extensions remain native; the host may inventory them with provenance but does not merge/override its config. Host extensions are scoped overlays injected only through an agent-supported session mechanism. The selected agent sees host MCP tools only through a filtered session MCP façade/tool injection that it negotiated; Gmail/Drive credentials remain in Core's vault and each operation has its own scope. If the agent cannot consume the overlay, say so and offer host-side execution or a compatible agent. Host skills enter its context only as a bounded pinned instruction overlay when supported. Namespaces resolve collisions; preview shows which tool/skill will actually run. Plugin pages list bundled skills/tools/agents/UI, dependencies, versions and permissions before enablement; installing a bundle grants none of its contents. Revocation blocks future Core calls and reconciles running work. Global install is never synonymous with global active access. Marketplace browsing is catalog-only; package download/import, local installation, app-account connection and per-Work activation are separate user actions. Remote community marketplace installs remain unavailable until publisher/signature, digest, update, revocation and rollback checks are implemented (`31` §6.1).

Machine observation is listed under Privacy & permissions with plain-language category grants, purpose, recipient, sampling state/cadence, retention, last read, provider/admin requirement and a Revoke/Delete History action. On the user's **first explicit open/request** of System Workbench, show a short in-app consent dialog before reading even basic CPU/memory values; likewise, if a user or agent requests a category without consent, hold the request and ask in the active UI before sampling. Core returns the complete typed set of missing local-consent and Work-share grants with `sampled=false`; if both are missing, the dialog may present separate choices together, but granting one alone leaves the Work waiting and no provider starts. Never show consent during installation, app launch or background startup. The agent-request dialog names the exact fields and purpose, and offers an initially unchecked control for each missing grant: local collection on this device and sharing those fields with the requesting Work. If one grant already exists, show its active scope and ask only for the missing grant; approving one never approves the other. The Work waits for the user's choice while unrelated work continues; the agent cannot approve its own request. The ordinary overview dialog explains what is read, why, that basic readings run only while requested or while the System page is open, that background history needs a separate cadence/retention choice, and that agent sharing needs separate task consent. Actions: **Enable local overview** / **Not now**. Suggested copy: “See how your computer is doing. AgentCowork reads basic performance values while this page is open. Optional history can continue on this device at the cadence and retention you choose. Nothing is shared with your agent unless you separately allow it for a task.” This gate controls only Core's Machine Observer capability. A discovered agent's native shell/OS tools follow its own effective policy and are listed separately; the dialog does not claim to block or authorize those calls. If a task needs an enforced boundary, show that isolation is available only when its binding actually provides it. If declined, collect nothing, keep the System page usable as an explanation, and show one inline note with **Enable** / **Keep off**; no repeat dialog unless the user explicitly reopens the permission control. In Processes, distinguish a normal process summary from Advanced diagnostics; opening that tab grants neither diagnostic consent nor OS elevation. Explain any requested fields in plain language, show protected/inaccessible processes as unavailable, and offer only exact one-time elevated reads when a provider requires them. The Observer adds no install-time privilege requirement. NSIS is the no-admin per-user consumer installer. The current pinned Tauri WiX MSI is machine-scope/admin-managed; label its UAC as installation-only and never as monitoring consent. For an optional protected detail, the shield-marked “Read this detail once” action itself names the field, why standard access is insufficient and the fallback; clicking it opens Windows' UAC consent/credential UI directly, with no redundant AgentCowork confirmation popup. A standard user may need an administrator's credentials. If denied/canceled, preserve standard-user readings and show one non-error in-panel explanation of the missing detail with **Try this read once** / **Keep standard access**. Example: “Allowing this one read adds [field] to the process details. Your CPU, memory and storage overview still works if you skip it.” No repeated pressure; remember dismissal in non-authoritative UI preferences only. No preference grants data access, no prompt appears during polling or on launch, and no global “run as administrator” switch is offered.

## 8. Teams, long work and automations

The user sees one lead and a task list by default. Expanding Agents shows host-assigned workers and child relationships, assigned outcomes, current action, handoff, artifacts, usage and blockers. The Agent picker also links to **Manage subagents**. In that panel each eligible worker has a user-owned enable switch, pinned model/`Agent-managed` state, role, grant ceiling, isolation and concurrency limit; showing an agent in discovery does not make it eligible. The lead may delegate to (1) itself as a fresh child session, or (2) another explicitly enabled installed/discovered agent. Model and tool support are verified before dispatch. A lead may request a different-engine specialist (for example an external coding agent, GUI agent or local-model worker); Mission allocates a bounded PlanNode/Work with a contract and isolated resources. The lead's **native** subagents are not intercepted; report them only if the agent exposes lifecycle events. Host-level collaboration uses task handoff, scoped artifact refs and result mailboxes, with integration and independent verification before a shared outcome is marked done. Parallelism is chosen for independent work; no unbounded “swarm” toggle. The user can cap concurrency and replace a worker without losing the Mission.

Automations show Saved, Running, Scheduled and Needs attention. A recorded browser/desktop sequence can become a candidate skill with steps, selectors, inputs, secrets removed, scopes, expected results and failure conditions. A stable procedure can be compiled into a versioned workflow; a workflow can be packaged as a skill describing when/how to invoke it. Conversion never silently publishes or grants wider access. Managed browser/desktop steps remain capability calls with verification, while external agent-native steps retain their separate provenance. Events and schedules resume through existing Work/Workflow ownership; there is no additional execution loop.

## 9. Interaction and quality acceptance

At minimum, validate: a new user can send a normal message and open an artifact without learning architecture terms; agent/provider/auth limitations are accurately displayed; `+`, `@`, `/`, picker and access chip work by keyboard and screen reader; generated vs uploaded and indexed vs unindexed remain distinct; Workbench edits target the selected version and survive interruption; safe fallback exists for unsupported office content; active task/agent/child state is visible without reading traces; a takeover re-snapshots; and all claimed verification links to evidence. Measure task completion, time, errors, user interventions, comprehension and accessibility on nontechnical and technical cohorts separately. `ARCH/49-TEST-CASES.md` specifies reproducible scenario oracles and reporting.
