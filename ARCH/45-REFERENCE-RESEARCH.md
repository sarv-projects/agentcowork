## MCP SDK review (DEC-061)

The official Rust SDK release list shows the signed `rmcp-v3.4.0` release dated 2026-09-15. At that immutable tag, [`streamable_http_client.rs`](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.4.0/crates/rmcp/src/transport/streamable_http_client.rs) defines a public `StreamableHttpClient` trait that injects the HTTP request/response boundary, and [`model.rs`](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.4.0/crates/rmcp/src/model.rs) includes both `ProtocolVersion::V_2026_07_28` and `V_2025_11_25`. It also declares `LATEST` as `2025-11-25`, so the host must explicitly negotiate/advertise the intended protocol version. The SDK feature graph distinguishes the generic HTTP client from its `reqwest` implementation in [`Cargo.toml`](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.4.0/crates/rmcp/Cargo.toml). The official [2026-07-28 SDK table](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/sdk.mdx) lists Rust as Tier 1; an older dated 2025-11-25 SDK table says Tier 2, so that older status is not current evidence.

**Design consequence:** this source evidence invalidates DEC-048's factual premise that a custom Guard transport seam is missing and removes its reason for a hand-written protocol core. It does not prove that `rmcp` can be safely integrated without qualification. DEC-061 therefore selects the official SDK behind a Core-owned custom HTTP adapter; it forbids the default `reqwest` route for guarded calls and keeps all authorization, SSRF/DNS/redirect policy, credential custody, per-server compatibility choices and receipts in AgentCowork. Before replacing existing behavior, implementation must test actual Guard invocation, redirect refusal, DNS rebinding, origin validation, response/event bounds, cancellation, stdio child cleanup, both protocol revisions, `server/discover`, malformed headers and the lease-less/method-restricted/session-less `initialize` exception. Upstream protocol tests or tier labels cannot establish those product-specific guarantees.

**Limits:** this is an exact-source inspection of transport/model/feature declarations, not a full line-by-line source audit or a runnable integration spike. `rmcp-v3.4.0` is the initial reviewed dependency pin, not an automatic forever pin; dependency review, API-fit verification, license/security review, local compile, protocol parity and AgentCowork tests remain required in `TODO.md` (`TASK-PROV-003`). No code is copied.

### Official platform and runtime references

Microsoft's [application manifest guidance](https://learn.microsoft.com/en-us/windows/win32/sbscs/application-manifests) and [least-privilege guidance](https://learn.microsoft.com/en-us/windows/win32/secbp/running-with-administrator-privileges) say most desktop apps should run as `asInvoker`; unnecessary elevation increases attack surface, and operations that genuinely need admin can be split into an elevated helper. Microsoft's [UAC UX page](https://learn.microsoft.com/en-us/windows/win32/uxguide/winenv-uac) recommends useful read-only information remain available to standard users, a shield on the exact command that needs elevation, and elevation as late as possible; the page itself says its detailed design guide was written for Windows 7 and not updated for newer Windows, so qualify current presentation on every supported Windows build. This supports the chosen UX: first-use in-app consent dialog and explicit category consent precede collection; the Observer does not require install-time elevation; exact provider-proven privileged reads use a shielded command and one-shot helper. It would be inaccurate to assume all read-only computer data needs administrator access. This repository pins Tauri CLI `2.11.4` in `pnpm-lock.yaml`. Its [WiX template](https://github.com/tauri-apps/tauri/blob/tauri-cli-v2.11.4/crates/tauri-bundler/src/bundle/windows/msi/main.wxs#L20-L26) sets MSI `InstallScope="perMachine"`; `src-tauri/tauri.conf.json` does not override the template. By contrast, NSIS is configured `currentUser`. The recommended no-admin consumer path is NSIS; the current MSI is machine-wide/admin-managed and must be labeled as such. Installer UAC authorizes installation only, never data collection. A denied/canceled UAC leaves standard readings usable; one contextual non-error explanation is shown without re-prompting. See [Tauri bundler configuration](https://v2.tauri.app/reference/config/) and `SUPPORT-MATRIX.md` for the implementation qualification point.

For the optional process-diagnostics scope, Microsoft's [process security and access-rights reference](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights) says `OpenProcess` checks the process security descriptor and defines distinct query, memory-read, handle-duplicate and control rights; its [process enumeration guidance](https://learn.microsoft.com/en-us/windows/win32/procthread/process-enumeration) states that users can enumerate the process list while protected processes may still reject opening. [`QueryFullProcessImageName`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamea) accepts limited query rights. This supports per-field least-rights reads and typed access-denied results, not a global administrator mode. The need for any UAC helper remains provider-specific and must be measured on supported Windows builds.

GPU coverage is provider-specific: [NVIDIA NVML](https://docs.nvidia.com/deploy/nvml-api/latest/index.html) exposes supported GPU telemetry, but [NVIDIA's CUDA on WSL guide](https://docs.nvidia.com/cuda/wsl-user-guide/) explicitly notes query limitations under WSL. Runtime-specific inference measurements may come from documented endpoints such as [vLLM metrics](https://docs.vllm.ai/en/latest/design/metrics/) or [llama.cpp server metrics](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md); GPU utilization alone cannot establish tokens/sec or attribute work to a model.
